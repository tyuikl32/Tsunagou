## 急需解决的问题

### P0：租约生命周期与 Agent 执行节奏不匹配

- 实际资源 TTL 为 120 秒，记录有 12 次 `resource.lease.expired`、11 次领取、11 次 workspace.select、9 次 workspace.prepare，但最终业务提交只有 2 次。这些次数包含早期 assignment 与后续 attempt，不应全部解释成同一个任务失败。
- 本轮遇到租约在准备、协商、推理期间消耗的问题。事件 360 的 task.start 到事件 361 的到期仅约 15 秒，说明“已经允许开始”并不意味着获得一个合理执行窗口。
- 执行期间已有进度续租能力；问题不是完全没有续租，而是准备期、续租时机、宿主回合与回收之间没有形成可靠闭环。
- Full Access 下，撤销 daemon 授权不等于操作系统停止文件写入。不能把逻辑 fencing 描述成已具备宿主硬隔离。
- 最小修复方向：明确准备期保留与执行租约的边界；将有效执行窗口与 start 对齐；把机械续租交给能够判断执行存活的运行层；授权丢失要有明确停止/恢复反馈。范围及版本不变时复用工作区决策，避免主 Agent 每次重新批准相同选择。
- 不改变用户已确认原则：待领取任务不因无人领取而失效；长期等待用户不等于必须一直持有写租约。

### P0：实际 Desktop 会话自动唤醒仍未闭环

- 消息投递、入箱、ACK，与宿主开始一个新的 Agent 回合是不同事实。
- 当前落盘唤醒状态明确为 failed，错误为 `desktop_thread_unavailable`；相同记录后来出现 `agent_presented`，不能因此把先前唤醒失败改写成成功。
- 本轮曾通过 Codex 应用跟进消息推动 worker 继续工作；这证明应用能够触发对话，不证明 daemon 的宿主适配路径已成功。
- 本轮前期还存在未启用实际唤醒配置/绑定的问题；不能把错误配置与后续宿主控制连接问题混为协议本身不支持唤醒。
- 最小修复方向：使 daemon 的唤醒请求到达实际管理该对话的宿主控制端；接入时完成绑定，成功触发后记录实际 turn。无法自动唤醒时明确进入手动拉取模式，不循环重试同一种不可恢复错误。
- 验收必须从停止工作的原 worker 会话开始，由 daemon 消息触发新回合并处理该消息，不能用主 Agent 手动发消息代替。

### P0：少数状态转换存在真实性漏洞

- 契约 `6333274b-ff33-4d2d-bbd1-986ae661a208` 在事件 254 撤回，随后事件 267/268 接受代理确认，当前又为 accepted。源码 `accept_proxy` 缺少普通 accept 已有的 proposed 状态限制。
- 多个旧契约参与者只有 slot、required，没有 agent_id，无法满足正常参与者确认规则；新契约的完整参与者对象能够工作。应在提议入口统一结构并拒绝不完整对象。
- 两个旧任务在事件 395/396 请求取消后仍为 cancel_requested，且无 current_attempt_id。没有活跃 owner 的任务不应无限等待 owner ACK。
- 最小修复方向：修复代理确认的终态保护与参与者校验；无活跃 owner 时原子完成取消并同步 assignment。主任务等待用户最终确认是另一种情况，不应借此自动宣布项目完成。

## P1：效率和首次使用问题

### 将机械准备合并为可直接执行的入口

本轮多次在领取、工作区选择、资源声明/获取、准备、preflight、start 之间往返。部分 scope 格式或 root 绑定问题直到执行准备才发现；相同工作区选择在恢复后重复要求主 Agent 操作。

建议保留底层 owner、scope、revision、租约与事务校验，将稳定的默认流程封装成一次可恢复操作；发布前完成必要的范围规范化与 root 校验。主 Agent 负责业务分工、真实冲突和重大选择，不逐项操作机械流程。不要再增加一层需要 LLM 逐项填写的检测报告。

### 安装、运行和会话上下文需要一致

本轮历史症状包括安装源码副本与调试源码不一致、daemon 启动后退出、目标目录 CLI 无法定位运行包/凭据、旧 MCP bridge 保留旧 session、接入成功但工作区或唤醒绑定尚未准备完成。以上并非全部仍处于故障状态，本次未逐一重现。

建议一个可复制的初始化/接入命令固定源码版本、项目根、状态目录、当前对话身份和宿主绑定，返回可直接工作的结果及单一明确的失败原因。不要要求用户手填 agent_id/conversation_id 或反复猜测重载步骤。

本轮两个 completed Attempt 的 owner_agent_id 不同，不能把历史“同 IDE 不同对话被合并”的问题不加核实地算作本次仍未修复。

### 留痕需要记录失败及触发来源

- 当前事件具备时间戳和主体，能还原本轮任务 start、submit、review；不是完全没有持久化。
- 唤醒状态文件中有 failed，但诊断序列只有 wake_requested 和 agent_presented，缺少对应失败终态，也无法单靠 presented 判断是自动唤醒还是应用跟进。
- 应使拒绝、超时、失败、恢复可按 message/task/attempt/command 关联，区分请求时间、实际开始时间和完成时间。失败诊断不能伪造为业务成功事件。
- 本轮没有完整可验收的 OpenTelemetry 因果链。补关键链路的 trace/span 与既有事件关联即可，不先建立复杂观测平台，也不要求每个函数或每轮推理生成证据。
- 原汇总材料当前缺失也说明归档入口需要可靠：保存后应核对文件可读、入口可定位。不能仅凭会话中说过“已保存”完成验收。

## 业务应用自身的独立缺陷

代码检查发现 `Modules/Btid.cs` 的 Create 调用 CRC/HMAC 检查却忽略返回值；CRC 扇区循环在流读取返回 0 时也缺少明确退出。前者存在校验失败仍返回元数据的风险，后者存在截断输入导致循环不结束的风险。这里是源码确认的缺陷风险，本次没有重新运行损坏输入复现，不能称已实测所有异常样本。

这两项应在继续开放真实文件测试前修复；属于业务解析器，不应归咎于 A2A。正常样本成功、构建通过、UI mock 通过，均不能代替损坏文件和真实端到端验收。

## 建议下一轮范围

先补状态真实性漏洞，并修复租约/准备/恢复闭环和原会话自动唤醒；随后统一一键接入与机械执行入口，补必要的失败时间线。业务 BTID 缺陷独立处理。

暂不重写八模块，不扩大宿主矩阵，不增加审批、重复能力检测或新的业务状态机。下一轮验收应看到正常任务从接入、领取、执行到提交无需用户修 session、人工续租或手动催醒；真实冲突与重大用户决策仍保留明确边界。
