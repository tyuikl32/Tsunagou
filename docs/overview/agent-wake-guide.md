# 按需提醒与同机宿主唤醒补位

协作时先通过项目上下文读取其他 Agent 的真实宿主资料：Agent ID、宿主类型、版本、机器与证据。宿主不是模型品牌，OpenCode 使用 DeepSeek 模型仍然是 OpenCode。记住这些资料供判断；执行前由系统重新核对当前会话绑定，不能把旧资料当永久授权。

## 先选通道

| 双方宿主与范围 | 处理 |
| --- | --- |
| Codex → Codex | 固定走 Tsunagou 已有 Codex 唤醒通道，不提供补位 wake 命令；保留项目开关、绑定与重试规则 |
| 不同宿主、OpenCode → OpenCode、DSH → DSH | 既有通道未覆盖时，允许发送方显式使用已验证的同机补位入口 |
| 宿主未知或资料冲突 | 先核实，不猜宿主或原会话 |
| 跨机器 | 本轮补位不支持，返回原因并向 main 升级 |

已有原生唤醒仍在排队、派发或结果不明时，不叠加补位调用。Codex 通道失败也不能自动切换脚本或自行开启项目开关。hook 是临时补位指引，不是另一套自动调度器。

## 发送方直接操作

main 和 Worker 规则相同。需要对方处理的消息使用 `response_contract: {"required": true}`；发送后根据简短提示检查状态。定向派发任务和 Worker 提交待 main 审查的结果也会提示。普通查询、ACK、义务关闭和验收不重复唤醒长文。

首次已认证上下文读取提供完整指引；同一指引版本不会因 bridge 重启而重复。后续相同消息的相同状态不重复提醒，主动状态查询仍返回当前结果。

1. 调用 `coordination__wake_status`，参数为实际消息的 `message_id`，查看接收方、通道、状态和证据。
2. 返回补位执行入口且状态允许时，发送方自行调用 `coordination__wake`，使用同一个消息 ID。
3. 结果不明时回到状态查询。不要重复执行，不用 main 代办每一次 Worker 间唤醒。

这两个入口通过 MCP 认证原发送方。补位执行内部调用固定 PowerShell 脚本，并私下解析已核实的原会话与已安装宿主；**不要从终端伪造 sender、复制 bridge session 或使用用户 control token 代替 Agent**。返回的工具调用就是稳定执行入口，不需要每次查源码、拼私有端点或 UI 自动化。

## 如何理解状态

| 状态或能力 | 含义与操作 |
| --- | --- |
| 未运行 / idle | 当前宿主明确证明原会话空闲；不是由最后活跃时间推算 |
| 正在处理 / running | 宿主观察到活动回合；只有关联证据才说明正在处理本消息 |
| 可以排队 / can_queue | 独立能力；忙碌不自动表示可以排队 |
| 状态未知 / unknown | 缺少可靠事实；先查状态，不盲目启动 |

同一请求已运行时不再启动。处理其他请求时，只在宿主明确支持且已有授权允许时排队；不打断现有工作。

四项进度分别呈现：**Tsunagou 已接收消息、宿主回合已启动、接收方已展示/读取、已有相关业务回应**。ACK、入队或命令退出成功不能替代其他阶段的证据，业务回应也不自动等于问题已解决。

## 宿主脚本

**OpenCode**：当前脚本验证版本为 **2.0.18**，同时检查 CLI 和运行服务版本。通过已安装的 `opencode api` 访问宿主自带认证通道；不直接拼接带凭据的 HTTP 请求，也不传 `--server` 绕开托管服务认证。先证明原会话存在，再查询或驱动该会话；会话工作目录允许不同于协调项目目录。不能使用可能创建新会话的任意 ID，不添加 `--auto`，不改变审批模式。其他版本明确标为未验证。

脚本返回统一状态、执行结果及错误，不能把提示已提交冒充回合已启动。当前 OpenCode 活动接口不提供本消息对应的回合关联，因此通用返回不会仅凭活动状态把 `host_turn_started` 设为真。实际测试的范围及限制见 [本轮验收记录](../acceptance/agent-wake-assistance-2026-10-04.md)。

**DeepSeek Harness**：Desktop、Web、TUI 分别核实。历史 Web `session/prompt` 的 `queue|steer` 证据不证明普通 Desktop 可用同一接口。未验证形态返回明确的 `unsupported` 和原因，这属于本轮明确接受的降级；不让 Agent 无限研究或临时下载其他版本。证据背景见 [DSH 验收记录](../acceptance/deepseek-harness-11-baseline-2026-10-01.md)。

**Codex**：双方均为 Codex 时继续使用 [已有通道](../implementation/codex-host-wake.md)，补位脚本不调用它。其他宿主发往 Codex 时，也只能使用已有验证路径或明确返回未覆盖，不猜测 Desktop 通用恢复命令。

## 失败时自行核实并收口

先核对是否认错目标厂商/宿主，再核对版本、所在机器、原会话和入口。根据新证据纠正；超时或结果不明时先查目标是否已经开始处理，避免重复回合。明确不支持时停止当前路径，保留具体错误。

Worker 无法解决时向 main 升级一次，附消息 ID、已核实宿主、尝试入口和失败原因；main 无法解决则记录阻塞，不循环给自己发消息。**不要要求用户手动唤醒，不反复配置、探测、重绑 Tsunagou 自动唤醒，不伪造成功或扩大权限。** 唤醒本身不授权接入新 Agent、读取对方私有收件箱或代用户确认项目完成。

长指引保留在本文；安装更新后重载 bridge，已有项目通过 `tsunagou project bootstrap --refresh` 更新常驻上下文。当前支持和实测证据以本机安装版本为准；未发布修改不能由在线文档证明。
