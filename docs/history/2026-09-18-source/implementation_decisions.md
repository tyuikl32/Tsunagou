## 已确认：Agent 范围与身份

| 编号 | 决定 | 具体范围 |
|---|---|---|
| D16 | 仅以宿主证据延续会话身份 | 宿主能验证为原会话恢复或上下文压缩时保留 `agent_id`；新建、清空和分叉会话均创建新身份，分叉只记录来源关系。无法证明连续性时必须重新接入。 |
| D17 | 任务级继任，可整体退休 | 主 Agent 可按任务原子移交执行权、租约与未处理消息；也可一次移交全部未完成任务并退休旧身份。历史作者和契约接受者保持原身份。 |
| D18 | 长期项目身份与短期凭据分离 | `Project` 持续到用户归档或删除；成员身份持续到被移除、退休或项目结束；加入票据单次兑换且短期有效，访问令牌可过期和轮换而不改变 `agent_id`。 |
| D19 | 单一主 Agent 与授权代次 | 每个项目同一时刻最多一个主 Agent；用户始终可任命或撤销，主 Agent 仅在项目策略允许时原子交接。交接递增 `authority_epoch`，旧代次的管理命令失效，离线不自动选主。 |
| D20 | 逻辑授权与机械执行分离 | 用户分别设定调度中心和主 Agent 的权限上限，普通 Agent 权限取两者与本次授权的交集。主 Agent只能收窄；只有用户可扩大或授予 Full Access。宿主是否能机械拦截另以执行强度声明，不能把自然语言约束标成沙箱保护。 |
| D21 | 按资源能力记录四级执行强度 | 每类资源能力分别标记 `advisory`、`observed`、`gated` 或 `isolated`。任务可要求最低级别；不足时禁止自动分派。项目策略可允许主 Agent 留理由显式降级，也可严格禁止降级。 |
| D22 | 固定能力 + 带范围授权 | 角色只是授权模板；实际判断使用固定 capability、资源选择器、allow/deny、有效期、签发者和授权代次。权限逐层取交集，显式拒绝优先；首版不引入通用策略脚本。 |
| D23 | 具名多根与规范资源 URI | 项目以多个 `ProjectRoot` 覆盖跨目录/跨仓库；授权引用 `fs://{root_id}/{relative_path}`。路径按平台规范化并解析链接逃逸；Full Access 是独立显式标识。 |
| D24 | 项目初始化即建立项目内持久化 | 用户否定“全部项目共用中央数据库且项目目录无控制数据”。每个项目从初始化起必须拥有项目内协调存储，基本协作上下文随项目维护；具体分层见 D25。 |
| D25 | 项目内 Git 共享层 + 本机运行层 | `.tsunagou/` 同时包含可由 Git 跟踪的项目清单、策略、任务/契约/认知快照、已完成事件段与检查点，以及默认忽略的 `local/` SQLite、令牌、租约、连接和缓存。新克隆从共享层恢复并开启新运行代次。 |
| D26 | 事务物化队列 + 检查点屏障 | 协作变更在 SQLite 事务中登记共享层物化；默认等待原子文件写入再成功。已提交但未物化返回 `202 pending_materialization` 并幂等重试。交接、完成、归档和 Git 提交前必须通过 checkpoint；系统不自动 commit/push。 |
| D27 | 协作历史只自动 fast-forward | checkpoint 形成带父哈希的历史链。外部变更只有可证明为后继时自动导入；分叉时停止写入，可自动合并不同实体，同实体冲突由主 Agent 处理，身份/权限上限冲突由用户处理。运行态不参与 Git 合并。 |
| D28 | TOML 配置 + JSON 状态 + NDJSON 事件 | 人工配置用 TOML；权威快照用带版本且经 JSON Schema 2020-12 校验的 JSON；封存事件用 NDJSON。内容以 RFC 8785 JCS 规范化后做 SHA-256；Markdown 仅为派生视图，首版不使用 YAML 或签名。 |
| D29 | UUIDv7 + 三种顺序边界 | 实体、命令、消息和事件使用 UUIDv7；聚合 revision 管并发，本机 runtime_epoch/event_seq 管实时顺序，checkpoint 父哈希与因果字段管跨克隆历史。UTC 时间戳仅作事实时间，不作顺序权威。 |
| D30 | REST/MCP 共用应用命令信封 | 查询使用 `/api/v1` 资源 URL，转换使用显式 actions。命令携带 command_id、expected_revision、必要时 authority_epoch 和 payload；command_id 同时作幂等键。错误用 RFC 9457，主版本在 URL。 |
| D31 | 收件箱确认分层 | 消息分别记录 enqueued、leased、fetched、可证明时 presented、显式 acknowledged/disposition，以及 deferred、expired/dead-letter。重投按 message_id/attempt 幂等；确认消息不能替代请求所需的领域响应。 |
| D32 | 三类消息 + 发送时收件人快照 | 消息顶层为 notification、request、response；request 声明响应契约，response 以 in_reply_to 关联。路由在发送事务中展开为逐 Agent 不可变记录；历史回放显式请求，优先级只控制投递顺序。 |

### 项目周期、对话身份与继承

用户要求已确认：

1. 票据发放与项目生命周期关联。
2. 同一项目周期内，Agent 能识别自己的身份并与自身对话上下文对应。
3. 同一厂商的新建空对话必须重新接入，不能沿用旧 Agent 身份接管任务或事件。
4. 同厂商多个对话允许同时以不同身份加入。
5. 新 Agent 成为旧 Agent 的继承者，须经主 Agent 确认，再重新分配旧任务。

加入票据、访问令牌、主 Agent 唯一性、适配器降级和继任 attempt 处理已在 D18-D19 及 [第二轮账本](./implementation_decisions_round2.md)中继续确定。各宿主连续性证据的具体字段仍需在适配器字段表中落实。

身份连续性规则已确认：

- 原会话恢复和上下文压缩只有在宿主能提供可验证证据时延续原 `agent_id`。
- 新建、清空和分叉会话必须创建新 `agent_id`；分叉可记录 `forked_from_agent_id` 或等价来源关系，但不能继承执行身份。
- 无法取得或验证宿主会话证据时按新会话处理并重新接入，不能依据模型自述、显示名称、工作目录或旧令牌恢复身份。

继任规则已确认：

- 继任关系由主 Agent 确认，但它本身不改写历史身份。
- 默认以任务为单位，在一个协调器事务中移交执行权、相关租约和未处理消息责任。
- 主 Agent 可选择全部未完成任务完成整体替代，并同时退休旧身份。
- 已完成任务、历史消息作者和历史契约接受者继续归属于旧身份。

项目与凭据生命周期已确认：

- `Project` 是长期协作空间，持续到用户归档或删除，而不是随守护进程启停重建。
- `agent_id` 表示项目内成员身份，持续到成员被移除、退休或项目结束。
- 加入票据只能兑换一次且短期有效；它不能作为长期 API 凭据。
- 访问令牌可以过期、撤销和轮换；令牌变化不创建新 `agent_id`。

主 Agent 规则已确认：

- 每个项目在任一时刻至多一个主 Agent；允许暂时没有主 Agent。
- 用户保留任命和撤销主 Agent 的最终权限。
- 当前主 Agent 只有在项目策略明确允许时，才能把角色原子交接给另一已注册 Agent。
- 每次任命、撤销或交接都递增 `authority_epoch`；管理命令必须携带或绑定预期代次，旧代次立即失效。
- 主 Agent 离线或租约失联不会触发自动选主，避免系统在缺乏用户意图时扩大其他 Agent 的权限。

权限包络与执行现实已确认：

- 用户分别为调度中心和主 Agent 设置多个授权根目录或 `Full Access` 上限。
- 普通 Agent 的逻辑权限是调度中心上限、主 Agent 上限和本次授权的交集；主 Agent 可缩小、拆分和回收，但不能扩大任一用户上限。
- 只有调度中心与主 Agent 都由用户授予 `Full Access` 时，主 Agent 才能向其他 Agent 授予 Full Access。
- 逻辑权限不等于宿主机械权限。为避免 IDE/Harness 自身限制工作，Agent 可以在宿主中保持 Full Access，而由调度中心通过系统消息、自然语言和可用的 Hook/插件约束其行为。
- 每个适配器必须如实声明执行强度。无法动态修改宿主设置或拦截某类工具时，只能标记为提示约束或可观察约束，不能宣称已强制阻止越界。
- 调度中心自己的 API 权限、任务代次、租约与管理命令仍由服务端机械校验；上述限制主要针对 Agent 绕过调度中心直接操作文件、进程、网络或 IDE 工具的情况。

执行强度协议已确认：

- `advisory`：系统消息、自然语言或工作说明约束；无法观察或阻止所有实际操作。
- `observed`：能在操作时或操作后取得证据并报告，但没有可靠的执行前阻断点。
- `gated`：Hook、插件或受控工具能在执行前向策略层查询并允许或拒绝该操作。
- `isolated`：宿主沙箱、操作系统、容器或等价机制形成 Agent 无法通过普通工具绕过的实际边界。
- 等级按文件读、文件写、命令执行、网络、调度中心 API、IDE 工具等资源能力分别记录，不能用一个 Agent 总等级掩盖部分覆盖。
- 任务可声明每类能力的最低等级；适配器不满足时调度器不得自动分派。
- 项目默认可授权主 Agent 显式降级，必须提交理由并产生审计事件；项目严格模式可禁止任何低于任务要求的降级。

权限表达模型已确认：

- 首版维护版本化的固定 capability 清单；角色仅是生成常用授权集合的模板。
- 授权记录至少包含主体、capability、资源选择器、allow/deny、有效期、签发者和 `authority_epoch`。
- 实际权限按系统硬约束、用户上限、项目策略、主 Agent 授权和任务临时授权逐层取交集；显式拒绝优先。
- 任务临时授权只能位于已有上限内，并随任务交接、完成、取消或过期被回收或重新签发。
- 首版不支持用户编写任意策略表达式或脚本；新增需求通过版本化 capability 和结构化资源选择器演进。

文件资源身份已确认：

- 项目可注册多个具名 `ProjectRoot`，每个 root 可代表目录、仓库或用户定义的业务区域。
- 授权、任务影响范围和租约统一引用 `fs://{root_id}/{relative_path}`；绝对路径只用于用户注册或更新 root 的管理操作。
- `Full Access` 使用独立的范围类型，不能以注册盘符根目录、`/`、用户目录或通配符来隐式表达。
- 路径按平台规则规范化；Windows 需要处理盘符大小写、UNC、junction、设备路径和长路径差异。
- 对 `gated`/`isolated` 操作，解析符号链接或 junction 后若目标越出所有授权 root 则拒绝；目标属于另一个授权 root 时重新归属到该 root 后判定。
- 业务上重叠的 root 可保留不同名称，但系统需要识别同一物理目标，避免通过别名重复取得冲突租约或绕过拒绝规则。

项目内持久化方向已确认：

- 用户明确否定单个用户级 SQLite 承载所有项目、项目目录默认不保存协调数据的方案。
- 从项目初始化开始就在用户指定的协调根中建立项目控制目录，使基本协作配置与上下文属于项目本身，而不是只存在于某台机器的用户级服务目录。
- 一个跨多个目录或仓库的项目仍需选定一个协调根；其他 `ProjectRoot` 通过稳定逻辑标识挂接。
- 用户级目录继续适合保存守护进程发现信息和项目注册索引，但不能成为项目协作状态的唯一保存地点。
- Git 共享层与本机运行层采用下述已确认划分。

项目内双层持久化已确认：

- 用户指定的协调根下创建 `.tsunagou/`；它是项目数据的一部分，不依赖用户级全局数据库才能理解项目。
- Git 共享层包含项目清单、逻辑 root 定义、项目策略、任务与依赖快照、契约、认知决策、已完成事件段和可恢复检查点。
- 本机运行层位于 `.tsunagou/local/`，包含当前 SQLite、收件箱投递游标、活跃租约、连接、访问令牌、进程信息和临时缓存，并默认写入 `.gitignore`。
- 跨机器共享的是逻辑 `root_id` 与可移植描述；绝对路径保存在本机绑定中，不能进入 Git 共享层。
- 新克隆从 Git 共享层重建本机数据库并创建新的 `runtime_epoch`；旧机器的令牌、连接和活跃租约不能通过复制仓库恢复。
- SQLite 是当前运行代次的权威事务状态；Git 共享层必须足以恢复基本协作上下文，因此不能只导出不可解释的数据库副本。

共享层物化与检查点已确认：

- 每个需要进入 Git 共享层的领域事务同时写入 materialization outbox；文件生成器按领域 revision 幂等执行。
- 共享文件使用同目录临时文件、刷新并原子替换，避免读到半写文件；具体跨平台 fsync 能力在实现计划中列出降级行为。
- 默认请求等待本次 revision 物化后返回成功。数据库已提交而物化失败时返回 `202 pending_materialization` 与 operation ID，客户端必须查询最终状态，不能盲目重发领域命令。
- 任务交接、任务完成、项目归档和准备 Git 提交前执行 checkpoint 屏障：清空 outbox、封存完成事件段、生成哈希清单并记录覆盖的领域 revision。
- 调度中心可以报告工作树需要提交的协作文件，但不自动执行 Git commit、merge、rebase、push 或 pull。

Git 历史导入与分叉处理已确认：

- checkpoint 清单记录 `project_id`、`lineage_id`、`checkpoint_id`、父 checkpoint 哈希及覆盖的领域 revision。
- 只有能验证为当前 checkpoint 后继的共享状态可自动 fast-forward 导入。
- Git pull、checkout 或外部编辑造成历史分叉时，项目进入 `diverged`，停止新的领域写入并保留只读查询。
- 双方修改不同实体时可按稳定实体 ID 自动三方合并；同一任务、契约、认知决策或普通项目策略冲突由主 Agent 解决。
- 主 Agent 任命、用户权限上限、项目/lineage 身份冲突必须由用户解决，不能由主 Agent 扩权式合并。
- 未 checkpoint 的本机变更与外部共享层变更相遇时不得静默覆盖或热重载。
- 活跃租约、令牌、连接、进程与运行中状态属于本机运行代次，永不通过 Git 合并或复活。

Git 共享层格式已确认：

- `project.toml` 与少量人工维护的策略使用 TOML；机器写入时保持稳定排序和格式。
- 任务、契约、认知决策、项目快照和 checkpoint 清单使用格式化 JSON，每份文档包含 `schema_version`，按 JSON Schema 2020-12 校验。
- 已完成事件段使用 NDJSON，每行一个完整事件对象；段封存后不可原地修改。
- 领域对象内容哈希按 [RFC 8785 JCS](https://www.rfc-editor.org/rfc/rfc8785.html)规范化表示计算 SHA-256；checkpoint 清单另记录共享文件的原始字节哈希。
- Markdown 是从结构化状态生成的人类/Agent 阅读视图，不参与恢复、合并和权限判断。
- 首版不使用 YAML，避免隐式类型和多解析器差异；首版不做数字签名，跨机器不互信场景再引入签名与密钥管理。

ID、时间与顺序规则已确认：

- 项目、Agent、任务、契约、命令、消息、事件、checkpoint 等持久实体使用 RFC 9562 UUIDv7。
- 时间字段使用 UTC RFC 3339 并保留微秒；时间戳不参与权限、并发胜负或唯一顺序判定。
- 每个领域聚合维护从 1 递增的 `revision`，作为乐观并发和实体三方合并基础。
- 每个本机 `runtime_epoch` 内分配单调递增 `event_seq`，用于 SQLite 提交顺序、SSE 游标和本机重放；跨克隆不可比较。
- 跨克隆因果关系由 checkpoint 父哈希链以及事件 `causation_id`、`correlation_id` 表达；分叉合并创建新 checkpoint，不重写历史事件 ID。
- 统一事件信封至少包含 `event_id`、`event_type`、`schema_version`、`project_id`、聚合类型/ID/revision、`actor_id`、`runtime_epoch`、`event_seq`、`occurred_at`、因果/关联 ID 和结构化 payload。

API 命令与错误协议已确认：

- REST 查询位于 `/api/v1/projects/{project_id}/...`；状态转换使用显式动作资源，例如 `POST .../tasks/{task_id}/actions/claim`。
- REST、MCP 和宿主插件桥接到同一应用命令信封：`command_id`、`expected_revision`、需要管理权限时的 `authority_epoch` 以及类型化 payload。
- `command_id` 是领域幂等键；HTTP `Idempotency-Key` 可镜像该值，但二者同时出现且不一致时拒绝。
- 查询响应返回与聚合 revision 对应的 ETag；跨传输的权威并发条件仍是命令信封中的 `expected_revision`。
- 错误使用 RFC 9457 `application/problem+json`，扩展稳定 `error_code`、`correlation_id`、`retryable`、当前 revision 与字段错误。
- API 主版本位于 URL；同一主版本只能增加可忽略字段或新端点，删除字段、改变既有语义或状态机必须升主版本。
- 同步完成返回 200/201；领域事务已提交但仍等待物化等情况返回 202 和可查询 operation 资源。

收件箱投递与确认协议已确认：

- `enqueued` 表示已持久加入目标 Agent 独立收件箱。
- `leased` 表示某个适配器连接取得限时投递权；租约到期且未完成时可由同一或后续连接重投。
- `fetched` 只证明宿主/适配器取得消息内容，不证明模型可见或业务处理。
- `presented` 只有在宿主提供消息已注入当前模型上下文的证据时才能记录；能力不足的适配器必须停在 fetched。
- `acknowledged` 需要 Agent 显式提交业务 disposition：`handled`、`rejected` 或 `superseded`。`deferred_until` 是非终态，到期后重新可投递。
- 超过业务期限进入 `expired`；超过可重试上限或持续不可投递进入 `dead_letter`，二者都保留审计事实。
- 所有投递状态变更以 `message_id`、`delivery_attempt_id` 和期望状态幂等处理。
- 要求响应的消息不能由 acknowledged 自动关闭；必须出现关联的结构化 reply 或相应任务/契约/协商领域命令。

消息语义与路由已确认：

- 顶层 `kind` 仅包含 `notification`、`request`、`response`；具体业务以版本化 `topic` 和 payload schema 表达。
- request 声明允许的响应类型、完成条件、期限和超时策略；response 使用 `in_reply_to` 引用原 request 并通过相应 schema 校验。
- 消息包含发送者、领域对象引用、优先级、过期时间、结构化 payload 及可选的人类摘要；自由文本不能代替任务/契约/认知协商必填字段。
- 直达、主题订阅和影响图路由在发送事务中解析成逐 Agent 不可变 inbox 记录，保证重放得到相同收件人集合。
- 后加入订阅者不会自动收到历史消息；需要历史时使用有权限的显式回放命令，并生成新的投递记录。
- 优先级只影响同一 Agent 可投递消息的选择顺序，不绕过权限、依赖、执行强度或业务期限。

## 本轮技术证据

- [FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/)、[异步处理](https://fastapi.tiangolo.com/async/)支持已选框架方向；具体 SSE 实现仍需固定依赖版本。
- [SQLAlchemy asyncio](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html)、[Alembic](https://alembic.sqlalchemy.org/en/latest/tutorial.html)、[platformdirs](https://platformdirs.readthedocs.io/en/latest/)提供已选技术基础。
- [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)支持条件写入，[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)提供标准错误体；D30 已确认查询 ETag、命令 expected_revision 和 Problem Details 的职责边界。
- [SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html)包含 Last-Event-ID；它不能证明模型已经看到或处理消息，独立收件箱需要业务确认语义。
- [Idempotency-Key 草案](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header)在本次访问显示 expired draft，不应写成已发布 RFC。
- 2026-09-17 官方适配器研究见 [adapter_research.md](./adapter_research.md)。
- [Python `Path.resolve`](https://docs.python.org/3/library/pathlib.html#pathlib.Path.resolve)会解析符号链接并消除 `..`；仅做字符串前缀比较不足以保护目录边界。
- [Windows 路径规则](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)包含盘符大小写不敏感、UNC、相对路径和设备命名空间等差异；资源身份不能直接使用未经规范化的用户输入字符串。
- [MCP Roots](https://modelcontextprotocol.io/specification/2025-06-18/client/roots)可向服务器暴露工作区边界，但不提供操作系统级强制；本项目只把它当适配器上下文信号，权威授权仍在内部领域模型。

5. 项目、成员、宿主会话、连接与 token family 的生命周期已确认。

### 已发出的本轮问题

- P01（已确认）：四款均达到正式共同基线，主动唤醒与工具门禁按宿主能力增强。
- P02（已确认）：只有宿主可验证的原会话恢复或压缩保留身份；新建、清空和分叉创建新身份，分叉仅记录来源；无法证明时重新接入。
- P03（已确认）：默认按任务原子移交执行权、租约与未处理消息；允许一次移交全部未完成任务并退休旧身份；历史归属不改写。

- P04（已确认）：项目持续到归档或删除；成员身份持续到移除、退休或项目结束；加入票据单次短期兑换；访问令牌轮换不改变身份。

P02、P03、P04 确认后继续形成 D19；此句保留为第一轮推进记录。

- P05（已确认）：项目同一时刻最多一个主 Agent；用户可任免；策略允许时主 Agent 可原子交接；授权代次失效旧管理命令；离线不自动选主。
- P06（已确认并补充）：采用调度中心/主 Agent 双重权限上限和交集授权；宿主可保持 Full Access，但系统必须区分逻辑授权与实际可机械执行的强度。
- P07（已确认）：按资源能力使用 advisory/observed/gated/isolated 四级；任务声明最低要求，能力不足不自动分派；项目可允许留痕降级或启用严格模式。
- P08（已确认）：固定 capability 加带范围授权；角色仅为模板，显式拒绝优先，首版不做通用策略语言。
- P09（已确认）：具名多根、root 相对资源 URI、平台感知规范化、链接逃逸检查、物理目标去重和显式 Full Access。
- P10（原建议被否定，方向已确认）：不采用全局单库作为全部项目的唯一持久化；项目初始化即建立项目内协调存储，保证基本协作能力随项目维护。
- P11（已确认）：`.tsunagou/` 内分 Git 共享层和本机运行层；共享层可重建基本协作上下文，本机层承载 SQLite 与敏感/短期状态，新克隆开启新运行代次。
- P12（已确认）：领域事务通过 outbox 物化共享层；未物化返回 202 和操作 ID；关键边界必须通过 checkpoint；调度中心不自动操作 Git 历史或远端。
- P13（已确认）：checkpoint 父哈希链；仅 fast-forward 自动导入；分叉暂停写入并按实体三方合并，敏感冲突升级给用户；运行态不合并。
- P14（已确认）：TOML 用于人工配置，JSON Schema 校验的 JSON 用于权威快照，NDJSON 用于封存事件，JCS + SHA-256 用于内容校验，Markdown 仅为派生视图。
- P15（已确认）：UUIDv7 标识；聚合 revision、本机 event_seq 和 checkpoint/因果图分别承担并发、实时顺序和跨克隆历史顺序。
- P16（已确认）：REST/MCP 共享命令信封；command_id 幂等、expected_revision 并发、RFC 9457 错误、URL 主版本和 202 operation 语义。
- P17（已确认）：收件箱区分入队、投递租约、宿主获取、模型可见证据和业务确认；延后可重投，过期/死信可审计，请求必须由独立响应关闭。
- P18（已确认）：notification/request/response 三类；request 使用结构化响应契约；发送时展开收件人快照，历史回放显式进行，优先级不改变授权。

P02 至 P18 均已确认；任务、认知、租约及后续决定现见 [第二轮账本](./implementation_decisions_round2.md)。

### 继承流程的工程约束（后续设计必须处理）

- 撤销 API 凭据、递增任务执行代次、失效租约，只能阻止经过协调器验证的后续操作。
- 已启动的外部命令和 Full Access 下的直接文件写入可能继续；不能把凭据失效当作旧进程已停止。
- 需要定义交接屏障：哪些宿主能确认旧操作静止、哪些只能报警/暂停新写入、哪些应交由主 Agent 按证据决策。
- 已完成任务、历史消息作者、历史契约接受者不得改写成继承者；继承应新增关系和交接事件。
- 项目周期内稳定身份与短期连接凭据分开。第二轮 D93 已覆盖早期凭据方案：保留 10 分钟单次票据，首发改为随 HostSession 生命周期失效的本机 session token，不实现 access/refresh token 轮换。
