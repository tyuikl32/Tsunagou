# D191 远端 Agent 不接要碰文件的任务（拒绝，而不是警告）

日期：2026-10-03
状态：已实施

## 决定

跨机器接进来的子 Agent（入席时自报了机器名的那一个）**不能开工任何需要工作区的任务**：
任务的资源请求里带 `path` 那一行时，`task.begin` 直接拒绝（`remote_worker_cannot_hold_a_workspace`）。

不需要文件的那一半照旧，而且这才是跨机器的主要价值：读项目、收消息、答复、评审、纯推理。
本机 Agent 一个路径都不少。

## 为什么是"拒绝"，而不是"警告后允许"

工作区、基线与证据**按构造都是这台机器文件系统上的事实**：根绑定存的是绝对路径与物理身份
（`root.bind`），基线是把那些文件扫出来的（`WorkspaceEvidence.scan` 用
`self._binding(root_id)["absolute_path"]` 读盘），证据记的是那次扫描。

远端的代码副本是**另一台机器上的另一个目录**：主机读不到它、取不了它的基线，也无从知道远端改的是
不是批过的那几个文件。于是"批给远端的文件任务"会以一种最坏的方式失败：**看起来一切在范围内**
（主机自己的路径校验全过），而远端在它自己那份副本上改了同名文件 —— 这比直接失败糟得多，因为它
会污染证据的可信度（"改动范围"两边说的不是同一份文件）。

警告把判断推给运气；拒绝能当场给出真原因。所以选拒绝。

## 与 `driver_kind` 的关系（容易误解的一点）

`external` **不是**"工作在另一台机器上"，它的意思是"工作在主机上、但不在我们管的工作树里"
（例如外部准备好的目录）。所以这三种隔离方式（`shared` / `worktree` / `external`）对远端**一律不成立**，
判定里不需要区分它们 —— 只要任务要工作区，远端就不能接。

## 故意没做的那半边

原本还打算让远端在导入时自报"我这台机器有没有代码副本、在哪、对应哪条基线"（`agent import --copy`），
好让"有副本的远端"能接文件活。**这次没做，而且是有意的**：按上面那条，就算报了副本，主机也建不出
能指向它的工作区与基线 —— 那份自报在当下没有任何东西会消费它，属于冗余。等真要支持远端文件活时，
第一步是先把工作区/基线做成能指向另一台机器副本的形态，那时候再决定要不要报、报什么。

现状一句话：**远端想干文件活，就得在主机上干（或者把这个任务拆成不需要文件的活）。**

## 这不是安全边界

"是不是远端"来自入席者**自报**的机器名。所以这条拒绝保护的是**诚实的接入流程**（我们的 CLI 与桥总会
带上它），不是防住一个被改过的客户端 —— 那种客户端本来就能谎报别的东西，而且谎报成"本机"并不会让它
比今天多拿到什么。真正的安全边界仍然是票、会话、授权与资源租约；这里要守的是**一致性**：别让一次
"看起来在范围内"的开工，把证据变成空话。

正因为机器名是这条判定的信号，**自报的名字超长时是截短而不是丢掉**：丢掉等于把一台远端当成本机。
（换行/制表符只是抹掉，不会让整条名字作废。）
