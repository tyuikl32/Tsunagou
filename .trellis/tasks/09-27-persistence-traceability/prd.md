## 目标

用户能够通过命令行回答：某个项目事实是什么时候、由哪个身份、基于什么版本和证据产生的；失败或后续修复怎样发生；哪些事实可从本机和 Git 恢复。只记录足够解释协作的结论，不要求 LLM 提供隐藏思维链。

## 需求与验收

| ID | 用户结果 / 验收条件 | 责任任务 |
|---|---|---|
| PT-R01 | 每个新业务事件有服务端 UTC 毫秒时间、真实 actor、subject、状态/版本变化、command/因果引用；相同重试不产生新的业务时间；历史未知时间明确 null | PT1 |
| PT-R02 | enrollment/reconnect 的持久幂等结果没有可用 token/nonce；响应丢失不创建重复身份，旧库脱敏升级不丢业务历史 | PT2 |
| PT-R03 | 结果附件覆盖获准 scope 的内容差异，排除内部附件递归；能区分提交者、自报验证与实际执行证据，并记录采集时间 | PT3 |
| PT-R04 | 项目真相不在 JSON/SQLite 中互相冲突；初始化有 genesis；checkpoint 提交后物化、可列表验证，干净 clone 可显式恢复历史且不继承活动权限 | PT4 |
| PT-R05 | 不读 SQLite、不手工拼 HTTP 即可查看任务/消息/认知/工作区/审计；时间筛选、分页、责任时间线与导出均服从原查询权限 | PT5 |
| PT-R06 | 稳定连接的只读查询不推进领域 revision；传输诊断与业务历史分层；既有 wake/assignment 历史和用户反馈后的修复有可追踪关联 | PT6 |
| PT-R07 | 真进程、Windows、协议兼容、迁移/故障窗口和 CLI 操作单均有带时间与版本的验证结果；新旧文档不将计划当实现 | PT7 |

验收必须同时覆盖两个独立 Agent、消息协商、结果审查、用户完成决定和一次验收后的缺陷修复。Task completed 不等于用户接受项目整体完成。根/仓库登记不扩大用户选择的文件范围。

## 范围

七个子任务修复既有 Python daemon、SQLite、TypeScript bridge、协议与文档；复用原八模块，不引入新的业务数据库或第九模块。不将模块整体 JSON 投影全部改写为 ORM 表作为本轮前提。

## 不包含

Web 工作台；远程多租户认证；完整实验平台；多机器同时写/分叉自动合并；自动 Git commit/push；全量终端录制；操作系统级逐文件作者证明；强制收集 token usage；重新实现所有隔离驱动。原完整设计中这些能力继续保留为后续范围。

## 已确定原则

SQLite 是当前事实；事件和相关领域状态同事务；语义判断归 main；Full Access 不改变用户上限；Task 可长期 open/blocked，不以用户等待计时失败；秘密仅留在私有交付位置；主 Agent 控制 Git；完整旧历史不为降低噪声删除。只补可核验的历史时间，不以迁移时间替代发生时间。
