# 控制台接入：三种形态，说真话，不发空票

日期：2026-10-02。来源：用户确认"按建议做；界面不动，真没做的仍留在面板里、但被页面挡回去"。

## 问题

控制台替宿主接入，只有一种形状能成立：**页面只提名（项目、角色、昵称、宿主），身份和票由宿主里那个真实会话自己产生**（Codex 就是这一种）。其余宿主被硬塞进第二种形状——"控制台先签票、再等宿主来兑换"。而控制台不可能提前知道对方是哪个会话，只能自己编一个 id 写进票；真实会话报上来的是它自己的 id，两者对不上，bridge 就把这张票丢掉（它不能替别的会话花票）。结果是：**页面看起来在等，其实永远等不到**，最后只剩一句"票过期了"。DeepSeek 还更早一步：`/console/hosts` 把"有没有注册命令"当成了"能不能接入"，于是它被判成不支持，页面连准备请求都不发。

## 决定

1. **一个字段回答一个问题。** `GET /console/hosts` 的每一项用 `mode` 说明"点了下一步会发生什么"，只有三态：`console`（页面能办完）、`in_host`（只能在这个宿主自己的聊天里接入）、`unsupported`（还没做）。原来的 `supported` 不再使用——它回答的是"有没有宿主 CLI 注册命令"，那是实现细节，不是人问的问题。
2. **页面办不完的宿主，控制台不许签票。** `prepare` 对 `in_host` / `unsupported` 直接拒绝（`host_enroll_not_available`，带一句话说明该去哪），不产生票据文件、不留半成品。理由：给一个兑不了的宿主签票比拒绝更糟——它看起来像有进展。
3. **DeepSeek Harness 就是 `in_host`。** 它在自己的桌面聊天里接入（宿主里已有这个动作），控制台不参与、不排队。宿主表里为它写了那一句人话，页面照实说。
4. **OpenCode 是 `console`，但它需要一个名字。** OpenCode 认的是"开会话时用的那个名字"，而这个名字可以由接入方先定：控制台发一个 `ses_<profile>`，票绑它，页面把"用这个名字开会话"这句话说给人；人用同一个名字打开会话，两边的身份就对上了。重试沿用同一个名字（`host-identity.json` 记住了它），不会一次换一个会话。
5. **真没做的（Claude Code、ZCode）仍是 `unsupported`。** 面板里留着这两项，页面在"下一步"处挡住并说明；HTML/CSS 与页面元素不动（界面是用户的作品）。

## 验收与边界

- 单测覆盖：三态取值；`in_host` / `unsupported` 在签票前被拒、且不产生票据文件；OpenCode 的票、`next` 与重试名字一致。
- 集成测试（真 daemon + 真 bridge）覆盖：不是票上那个会话的调用被拒（`not_enrolled`）且票据仍在；票上那个会话接入成功；控制台随后报 `arrived`。此前所有控制台接入测试都换掉了 daemon 与宿主登记、从不启动 bridge，所以这一条才一直没被发现。
- 边界：控制台仍只在本机、同一 OS 用户内工作。OpenCode 的 `console` 形态依赖"人按页面给的名字开会话"；不按名字开会话仍然是接不上，但这次是**页面说清了名字**，不是沉默等待。

## 补充（同日）：`in_host` 也有了等待界面

第 3 条决定的是"控制台不签票、不排队"——这一点没有变。补上的是**界面**：`in_host` 不再只弹一句话就结束，
而是开与等票那条路**同一块**等待遮罩，把宿主表里那句 `note`（"在目标聊天里让它接入 Tsunagou"）连同项目目录
摆在遮罩上，并每 2 秒问一次新的只读出口
`GET /console/projects/{project}/enrollments:observe?adapter=<adapter>&baseline=<开等时的席位>`。

到达与否仍由中间层判，理由与第 2 条同源（否则页面就在替后端猜）：名单里出现一个**不在 `baseline` 里**、
而且能由接入材料（`.tsunagou/bridges/<adapter>-*`、onboarding 目录 —— 读名单那条路会把它变成档案里的厂商）
**证明属于这个 adapter** 的席位，才算到了。认不出来历的新席位不算 —— 宁可继续等，也不替别家认领一次接入。

没有票，所以没有"过期"：收场只有到了 / 人点了「停止等待」（那一步会撤掉刚记下的那条申请，因为既无票可作废、也无宿主登记要注销）
/ 盯满 15 分钟。刷新后不恢复观察：服务端没有这条记录，因为它本来就不是一次"申请"。

**后续修正（同日）**：第 2 条"`prepare` 对 `in_host` 直接拒绝"已经作废 —— 用户实测发现聊天里根本不知道自己该接哪个项目，
所以 `in_host` 现在也走 `prepare`，但只写一条**不含票**的机器级待接入记录（原有决定"控制台不签票、不排队"仍然成立）。
