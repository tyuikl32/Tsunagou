# 接入时的项目从哪来：机器上一条待接入记录

日期：2026-10-02。来源：用户实测发现——在不同宿主里说"请接入 Tsunagou"，Agent 都不知道自己要接哪个协调根、什么角色，只能反过来问用户。用户明确：**同一时间只可能有一个 Agent 待接入，它的项目与角色是唯一的**，机器上本该答得出来。

## 问题

一句"请接入 Tsunagou"到达聊天时，聊天手上只有宿主给的两样东西：**自己的会话标识**和**工作目录**。协调根从这两样都推不出来：

- 项目可以协调多个文件夹（[子 Agent 指南](../overview/subagent-guide.md)明说工作目录不必是协调仓库）；
- 控制台建项目建在**自己的项目根**（`~/Tsunagou/projects/<名字>`），用户的业务工作区往往在别处。

而"待接入"这份唯一真相当时被存在三个不同的地方，只有一处是聊天读得到的：

| 宿主 | 记录在哪 | 聊天读得到吗 |
|---|---|---|
| Codex | 机器级文件 `console-enrollments/enrollments.json`（`EnrollmentStore`），带 `project_root`/`requested_role`/`nickname` | 读得到：`agent join` 先读它，再把 `project_root` 设为解析根 |
| OpenCode | 控制台**进程内存**里的记录 + 写进**项目目录**的票与 MCP 条目 | 读不到（除非会话正好开在项目目录、且 MCP 已加载）；控制台一重启连内存里那份也没了 |
| DeepSeek Harness | 什么都没有（`prepare` 直接拒绝） | 读不到 |

结果是：工作目录不是协调仓库时，除 Codex 外的宿主都只能顺着 cwd 找 `.tsunagou`（找不到时 `find_project_root` 返回 cwd 本身，于是"项目"成了一个空目录），再顺手翻机器上的项目清单，最后问用户"你要接哪个"。

## 决定

1. **一处存放，三条路共用。** 待接入记录一律写进机器级的 `EnrollmentStore`（每个 OS 用户同时只有一条 —— 这正是"唯一、毫无疑问"的依据）。它只写"哪个项目、什么角色、给哪个宿主、谁起的昵称"，**不含任何凭据**。
2. **`prepare` 对 `in_host` 不再拒绝。** 它写这条记录、返回宿主表里那句人话，然后页面进观察等待；**不签票、不写宿主配置、不登记 MCP**（票仍由那条聊天里的 CLI 以用户身份自己签）。`unsupported` 仍然拒绝。
3. **OpenCode 那条路也写这条记录**，顺带修掉"控制台重启就丢"的毛病。
4. **读它有三个入口**，顺序一致：显式指定（`--project-root`/`TSUNAGOU_PROJECT_ROOT`）→ 工作目录里真正的项目 → **这条记录**（此前两者都推不出时才用）。入口是 Codex 的 `agent join`、连接路径的解析回退，以及只读命令 `tsunagou agent pending --adapter <adapter>`。
5. **到达即让位。** 控制台确认 Agent 到达（名单里出现可证明来自该 adapter 的新席位）时关掉这条记录；页面「停止等待」也撤掉它。否则下一个 Agent 会被"同时只有一条"挡住。
6. **Agent 侧的话说清楚**：查不到记录就说"现在没有待接入的申请，请用户先在控制台准备"；**不要**从机器上的项目清单里自己挑，也**不要**为了让接入有个去处而 `project init` —— 接入是用户的决定。
7. **记录里的角色就是最终角色。** 页面上选主 Agent，那条聊天就只能以主 Agent 接入：`agent connect` 没给 `--role` 时用记录里的角色，给了冲突的角色直接拒绝（`enrollment_role_conflict`，在写任何桥材料之前）；页面等待遮罩上也写明"本次以主/子 Agent 身份接入"。daemon 那层本来就保证"角色只认票"：`agent.enroll` 的 payload 没有角色字段，席位角色取自票，票里是 main 时由 daemon 在就绪那一刻自行 `appoint_main`。**显示这一侧同样不许含糊**：`observe` 的到达判定要核对角色，席位角色不符时只报"连上了但角色不对"，不报成功、也不收掉记录（真正该来的那个还能用它）。

## 验收与边界

- 单测：`test_enrollment_store.py`（记录不再限 Codex、按 adapter 读、有主的记录不许别人收尾）、`test_agent_pending.py`（`agent pending` 的两种回答；连接路径只在 cwd 推不出项目时用记录，且不认别家的记录；**角色以记录为准、冲突即拒且不落任何桥材料**）、`test_console_enrollment.py`（`in_host` 只留记录、不签票、不写桥材料；到达后记录让位；**席位角色不符时只报没到位、记录留着**）。
- 前端冒烟：`in_host` 先 `prepare` 写记录，再开等待遮罩轮询 `enrollments:observe`；「停止等待」撤掉记录。
- 边界：记录是**用户控制面**的产物（控制台写、CLI 只读）。它不授予任何身份：认领、签票、入席仍然各自按原流程走；本机同 OS 用户能读它，与既有威胁模型一致（不新增秘密）。
- 仍未解决：OpenCode 的 MCP 条目写在**项目目录**里，会话不在项目目录时桥本身不会被加载。记录让 Agent 知道该去哪儿，但"在那儿开会话"这一步仍要求它照做；把注册改成用户级 + 每会话路由是适配器级变更，另行评估。
