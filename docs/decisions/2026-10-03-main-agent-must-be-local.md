# D195 只有本机能当主 Agent；项目永远有一个主 Agent；代次不当并发保护用

日期：2026-10-03
状态：已实施（"删除 Agent"另开一轮）

## 用户定下的三条原则

1. 只有用户能删除 Agent（删除本身下一轮做）。
2. 只有本机 Agent 能当主 Agent。
3. 项目永远有且只有一个主 Agent。

## 依据这三条做的改动

- **后端**：`appoint_main` 现在拒远端 Agent —— 判据是"入席时自报了机器名"（`Agent.machine`，
  跨机器导入那条桥填的），拒绝码复用 `console/enrollment.py` 发邀请时用的
  `main_agent_must_be_local`（同一个事实、同一个词），词表补了它的中文。
  拒绝时**不动原来的主 Agent** —— 拒绝就是什么都没发生。
- **页面**：跨机器的 Agent 不再画「设为主 Agent」按钮（判据 = 中间层标的 network 或自报的机器名）。
  这只是少让人误点；后端那道门才是真的（两道门都要，页面不是防线）。
- **确认框**：补了一句"原来的主 Agent 会变回普通成员" —— 换主是原子的，说清楚才不会让人以为
  会出现两个主 Agent。
- **不加**「撤销主 Agent」的入口：违反原则 3。后端那个动作留着，当"主 Agent 坏了、要恢复统筹"
  的应急手段（`cli-contract` 里原本就这么写），但不进页面、不进 CLI 帮助。
- **代次**：协议里声明了 `expected_authority_epoch`，但运行时没人读它。我们不打算用它当并发保护
  —— 两个窗口同时改主，后到的赢，结果仍然是"有且只有一个主 Agent"，正确性不依赖代次。
  页面不再带这个字段，注释改成说实话（以前一处注释说"不带会被拒"，那是过期说法）。
  协议字段留着，没有删（删它要动 schema 与生成物，收益不值）。

## 验收

- 单测：服务层与 wire 层都断言"远端被拒 + `main_agent_must_be_local` + 原主不动"。
- 前端冒烟：本机子 Agent 有「设为主 Agent」，主 Agent 与远端子 Agent 都没有（网络徽标照旧画）。
- 全量：既有换主/继任路径（`appoint`/`revoke` 的 20 多处调用）全部照旧。
