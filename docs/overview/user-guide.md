# Tsunagou 使用手册（面向使用者）

> 这份文档写给**用 Tsunagou 的人**，不写给改代码的人。照着做就能在一台机器上跑起来，
> 也能让第二台机器（虚拟机）加入同一个协作。
>
> 文中的命令是 Windows + PowerShell 下**实际验证过**的（2026-10-05）。跟开发有关的资料在
> [简明说明书](cli-http-manual.md)、[子 Agent 指南](subagent-guide.md)、
> [实施文档](../implementation/README.md)。

---

## 0. 它是什么，替你盯住什么

一句话：**让多个 Coding Agent 在同一个项目上协作，并且让冲突在动手之前就被看见。**

- **它替你盯住的**：谁在负责什么、每个任务做到哪一步、谁的活会和别人撞车、验收结论是什么、
  中途断线或换人之后怎么接着做。
- **你负责的**：定目标、决定谁能加入、拍板重大决定、验收成果。

## 1. 先认几个词

| 词 | 是什么 |
|---|---|
| **协调中心**（daemon） | 这个项目的"唯一真相"。所有 Agent 都向它汇报。跑在**主机**上。 |
| **控制台**（console） | 你打开的那个网页：建协作、接入 Agent、看进度。只跑在**主机**上，也只有主机自己能打开。 |
| **协作**（project） | 一个项目 / 一个目标。左栏一张卡片就是一个协作。 |
| **主 Agent** | 这个协作的调度者：拆任务、定改动范围、验收。**必须和协调中心在同一台机器上**。 |
| **子 Agent** | 真正干活的 Agent。可以在本机，也可以在别的机器（虚拟机）。 |
| **桥**（bridge） | 每台机器上把 Agent 接上协调中心的那个小程序。你在界面上点"接入"时自动配好，不用手写。 |
| **报号 / 邀请** | 让另一台机器加入的两个动作：那台机器先**报号**，主机据此打一张**邀请**，对方导入。 |

## 2. 第一次使用（只在主机上）

**前提**：这台机器有 Python 3.13、Node、pnpm。没装过就先跑仓库里的安装脚本
（`tools\dev\bootstrap.ps1`，或交给 Agent 走 `tools/install/install.py`）。

### 第 1 步：建一个协作

两种方式任选其一：

- **用控制台**：先起控制台（见第 3 步），在页面里"新建协作"。第一次用推荐这条。

  向导会在第 1、2 步之间再问一屏：**协作根目录、端口号、绑定地址、对外地址**。只在主机上用就一路保持默认；要让虚拟机连，选「可网络接入」并填上主机在 VMnet1 上的地址（例如 `http://192.168.32.1:2810`）—— 创建时控制台就会按这些值把协调中心起起来。
- **用命令**：`python -m tsunagou project init --name "我的协作"`

### 第 2 步：起协调中心

```powershell
python -m tsunagou daemon start --coordination-root "E:\Tsunagou\projects\我的协作" --host 192.168.32.1 --port 2810 --advertised-url "http://192.168.32.1:2810"
```

- `--coordination-root` 是**协作目录**（项目文件所在处）。
- `--host` 是"我在哪些网卡上听"。**只在本机用**就写 `127.0.0.1`；**要让虚拟机连**就得写虚拟机能到达的那张网卡地址（见第 3 节）。
- `--advertised-url` 是"别人该拨的号"，邀请里用的就是它。跨机器时**必须**写成一个虚拟机真能连上的地址。

看状态与停：

```powershell
python -m tsunagou daemon status --coordination-root "E:\Tsunagou\projects\我的协作"
python -m tsunagou daemon stop   --coordination-root "E:\Tsunagou\projects\我的协作"
```

### 第 3 步：起控制台

```powershell
python -m tsunagou web start          # 起页面
python -m tsunagou web status         # 看地址：Tsunagou console: running at http://127.0.0.1:2812
```

然后在浏览器打开那个地址。控制台**只监听本机回环地址**，别的机器打不开（也不需要打开）。

> ⚠️ **顺序要紧**：先起 daemon，再起控制台。**停控制台会把它启动的 daemon 一起停掉**
> （已知行为）。想让后端稳，就像第 2 步那样在**你自己的终端**里手动起 daemon。

### 第 4 步：接入主 Agent

控制台 → **Agent 管理** → 接入 → 位置选「**本机**」。按页面提示做完，名单里就会出现它。

### 第 5 步：告诉主 Agent 你要什么

在它自己的窗口里说目标就行。它会：拆任务 → 给每个任务写**改动范围** → 派给子 Agent →
收结果 → 验收。

### 第 6 步：看进度（左边栏那几屏）

| 屏幕 | 看什么 |
|---|---|
| 主视图 | 这轮在做什么、有没有需要你拍板的事 |
| Agent 管理 | 有谁、在不在线、点了能改昵称、能看它在哪台机器 |
| 任务区 | 每个任务的状态、负责谁、开工条件、**改动范围**；点一行看详情（含任务介绍） |
| 冲突与协商 | 分歧 / 冲突 / Agent 间协商 / 契约 |
| 租约审计 | 谁拿到了哪些路径的租约 |
| 验收与存档点 | 验收结论、存档点；等你确认的完成提案也在这里（两者故意合为一屏：确认完成本身就会落成一个存档点） |
| 工作区 | 隔离出来的工作区，以及文件占用情况 |
| 总路径 | 任务之间谁等谁，画成一张图 |

### 第 7 步：收工

在控制台里发起完工，按提示确认，最后停 daemon。确认动作在**主视图的"待用户决定"**里点进
"验收与存档点"那一屏；命令行的等价写法要带上提案自己的三个值：

```powershell
python -m tsunagou project complete <提案编号> --expected-project-revision <n> --digest <摘要>
```

## 3. 跨机器使用（虚拟机，host-only 网络）

这一节就是**本轮要测的流程**。拓扑很简单：主机跑协调中心与控制台，虚拟机跑一个子 Agent，
两边只通过 host-only 网络互通（虚拟机上不了外网）。

### 3.1 先决条件（三件事，缺一不可）

1. **两台机器网络能互通**。虚拟机网络模式选 **host-only（VMnet1）**。
   - 在**主机**上 `ipconfig`，找 `VMware Network Adapter VMnet1` 的地址（我这里是 `192.168.32.1`）。
     ⚠️ 本机可能同时有 VMnet8（例如 `192.168.153.1`）——**认准 VMnet1 那一个**，别搞混。
   - 在**虚拟机**里 `ipconfig`，找同一个网段的地址（例如 `192.168.32.128`）。
   - 双方互相 `ping` 得通。
2. **主机防火墙放行 2810**。本机已有一条入站规则 `Tsunagou daemon 2810 (host-only)`；新机器上照它加一条即可。
3. **两台机器上的 Tsunagou 是同一份代码（同一提交）**。这条最容易被忽略，见第 5 节"协议指纹"。
   虚拟机能出网（NAT）就直接在它上面装；只有上不了外网时，才需要**在主机上准备一份可用的代码目录，整份复制进虚拟机**
   （**别复制主机的 `.venv`** —— venv 里写死绝对路径，换台机器就废。代码可以整份搬，环境要在目标机上重建：`tools\dev\bootstrap.ps1` 装 Python 依赖、`pnpm install` 装 Node 依赖，桥也要在那台机器上构建一次）。

### 3.2 主机这边：把协调中心挂到虚拟机能连的地址上

如果 daemon 已经在跑，先停再按下面的方式起：

> 用向导建的项目（选了「可网络接入」）不需要这一步：控制台会按你填的地址把它起起来。这一节是给想自己指定、或改过网卡地址要重启的场合。

```powershell
python -m tsunagou daemon start --coordination-root "E:\Tsunagou\projects\我的协作" --host 192.168.32.1 --port 2810 --advertised-url "http://192.168.32.1:2810"
```

- `--host` 换成**主机在 VMnet1 上的地址**（不要写 `127.0.0.1`，那样只有主机自己连得上）。
- `--advertised-url` 必须和它一致 —— 虚拟机就是照这个地址来连的。
- 也可以写 `--host 0.0.0.0`（在所有网卡上听），但**对外地址仍要写具体地址**；
  0.0.0.0 会同时暴露在别的网络上，跨机器测试够用，但不必长期这么开。

### 3.3 虚拟机这边：先"报号"

在虚拟机里打开要用作子 Agent 的那个会话窗口，让它执行：

```powershell
python -m tsunagou agent whoami
```

它会打印**这条会话在宿主眼里的编号**。把这个编号告诉主机（复制过去即可）。

### 3.4 主机这边：打一张邀请

```powershell
python -m tsunagou agent invite --conversation-id <刚才那个编号> --nickname DSH-NET --role worker
```

- `--nickname` 是这台机器上这个 Agent 显示的名字（可以不起，起名更好认）。
- `--ttl` 默认 600 秒：**邀请是有寿命的**，过期就重新打一张。
- 命令会打印**一段可以复制的内容** —— 原样交给虚拟机（或者由控制台的「接入 → 位置＝网络」走同一件事）。
- 想不起来谁在等：`python -m tsunagou agent pending`。

### 3.5 虚拟机这边：导入邀请

```powershell
python -m tsunagou agent import "<把邀请原文整段粘进来>" --machine "DESKTOP-K03DV8N" --copy "D:\work\tsunagou" --baseline "main"
```

- **`--machine`**：这台机器的名字（自报的）。它会显示在主机界面 Agent 详情窗口的「在哪台机器」那一行。
- **`--copy` / `--baseline`**：这台机器上**代码副本的位置与基线**。**要让它做文件活就必须报**；
  报了的含义是"证据是它自报的"（主机不读那个路径）。不报，它就只做**不需要文件**的活。
- 导入完成后，在**那台机器的会话窗口里说一句话**（比如"继续"），桥才会把它真正接上。

### 3.6 回到主机：确认接上了

- **Agent 管理**里应出现这个 Agent；卡片右上角写着 **在线** 或 **离线**。
- 点开它（修改 / 详情）：能看到**在哪台机器**，以及**这台机器做不到什么**（例如"叫不醒它"）。

### 3.7 派活

- 你只管说目标，主 Agent 负责拆任务、写改动范围、派给谁。
- 远端**不能做文件活**时，让它把结果**发回给主 Agent**（消息），由主 Agent 落盘 —— 这是目前可靠的交付方式。

### 3.8 关机会看到什么（在线 / 离线怎么动）

| 情况 | 界面表现 |
|---|---|
| 远端正常 | 显示「**在线**」 |
| 远端关机 / 断网 | **90 秒内**变成「**离线**」（桥每 30 秒报一次心跳，连续三次没来就算走开） |
| 主机 daemon 刚重启 | 远端会**短暂**显示「离线」（最多 30 秒），之后各桥报到就恢复「在线」 |
| 远端的桥是**旧版本**（没有心跳） | 会一直显示「离线」。把新代码复制过去、重新构建桥即可 |

## 4. 日常操作速查

| 想做的事 | 命令 |
|---|---|
| 看协调中心状态 | `python -m tsunagou daemon status --coordination-root "<协作目录>"` |
| 停协调中心 | `python -m tsunagou daemon stop --coordination-root "<协作目录>"` |
| 起控制台 / 看地址 | `python -m tsunagou web start` / `python -m tsunagou web status` |
| 这台机器这条会话的报号 | `python -m tsunagou agent whoami` |
| 谁在等我接入 | `python -m tsunagou agent pending` |
| 打邀请（主机） | `python -m tsunagou agent invite --conversation-id <编号> --nickname <名字>` |
| 导入邀请（远端） | `python -m tsunagou agent import "<邀请原文>" --machine <机器名>` |
| 体检 | `python -m tsunagou doctor` |
| 任务历史 / 审计 | `python -m tsunagou task …` / `python -m tsunagou audit …` |

## 5. 必须知道的硬约束

1. **协议指纹必须一致。** 两台机器上的 Tsunagou 必须是**同一提交**；协议目录一改，
   `schema_bundle_digest` 就变，跨机器调用会被直接拒绝（报 mismatch）。复制代码过去时请核对。
2. **主 Agent 必须和协调中心同一台机器。** 它不能是虚拟机里那个。
3. **控制台只在主机。** 它只监听 `127.0.0.1`，虚拟机打不开也不用打开。
4. **停控制台会把它的 daemon 一起停掉。** 想稳就在自己的终端里手动起 daemon，控制台只当看板。
5. **远端做文件活必须先报代码副本。** 没报 `--copy` 就只能做不需要文件的活。
6. **唤醒只对装过唤醒插件的本机 DSH Desktop 会话有效。** 主机**叫不醒**别的机器上的会话（消息要等对方自己来取，桥每 30 秒取一次），也**叫不醒** OpenCode —— 它的 stdio 桥没有反向唤醒通道，bridge 如实报 `unsupported`；消息要等对方自己来取（桥每 30 秒取一次，
   所以不是"必须有人戳它"，但也**不会瞬间到**）。
7. **任务必须声明改动范围，租约和冲突才有意义。** 范围写成空（`{}`）时，系统按
   "这个任务不做文件改动"处理 —— **不占租约、不建工作区、也不会有路径冲突**。
   想让冲突机制真正跑起来，任务必须声明**真实路径**，而且两条任务的范围要**重叠**。

## 6. 出问题先看这几条

| 现象 | 先查什么 |
|---|---|
| 虚拟机连不上主机 | 互相 `ping`；主机防火墙 2810；daemon 的 `--host` 是不是写成了 `127.0.0.1`（那只有主机自己连得上） |
| `daemon status` 说 `daemon_identity_unverified` | 主机上 daemon 的 `--host` 与 `--advertised-url` 要对得上（这条已修，若仍遇到请记录） |
| 界面里远端一直「离线」 | 那台机器的桥是不是旧版（没有心跳）；或者它确实关机了 |
| 一条租约、一条冲突都没有 | 任务声明的范围是空的 —— 见第 5 节第 7 条，这是**本轮要专门验**的事 |
| 消息不自动到 | 远端要靠桥自己来取（30 秒一次）；唤醒只对**本机**窗口有效 |
| 装依赖失败 | 干净 clone 曾因锁文件缺一项而装不上（已修）；应急可加 `--no-frozen-lockfile` |

## 7. 本轮跨机器测试的检查清单

- [ ] 主机与虚拟机在**同一提交**（核对协议指纹）
- [ ] 虚拟机 `whoami` → 主机 `invite` → 虚拟机 `import` → 界面出现该 Agent，且显示**在线**
- [ ] 派一个**不需要文件**的活（远端把结果发回主 Agent），看它回到主 Agent
- [ ] 派一个**声明了真实路径范围**的活，并与另一个任务**范围重叠** → 应看到**租约 / 工作区 / 冲突**
- [ ] 在虚拟机里让它做文件活（先在导入时报 `--copy`），确认跨机器文件活这条路
- [ ] 把虚拟机**关机**，确认 **90 秒内**卡片变「离线」
- [ ] 重启主机 daemon，确认远端短暂「离线」后恢复「在线」


### 3.8 远端跑 OpenCode 时的差异（2026-10-05 补充）

- **不需要报号**：会话名由主机定（`ses_<名字>`），主机直接发邀请。
- **名字必须纯 ASCII**：它会进 OpenCode 的 HTTP 头，中文直接报 `invalid value`。
- **注册要在项目根目录做**：MCP 条目写进**当前目录**的 `opencode.json`，所以 `agent import` 必须在**你打算开会话的那个项目目录**里执行。
- **导入后要重载**：`opencode reload`，然后用邀请里那个会话名开一条**新**会话；核对用 `opencode debug config`。
- **没有 `.git` 也行**：GitHub 下载的 ZIP 快照可用（2026-10-02 实测）。
- **不能被后台唤醒**：它的 stdio 桥没有反向唤醒通道，主机叫不动，消息要等它自己来取。
- **`--copy` 只在接入时给一次**：它该指向**业务代码**目录，不是 Tsunagou 安装目录。
