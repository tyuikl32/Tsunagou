# 多 Agent 协作工作区：当前协调方案

## 一、项目定位

本项目不是单纯的多 Agent 调度器，也不是简单地把多个 Agent 放进不同 Git
分支。

目标是构建一个支持以下工作方式的协作工作区：

-   用户可以主动启动并加入新的 Coding Agent；
-   单 Agent 可以独立完成"规划---实现---验证---记录"的完整生命周期；
-   多个 Agent 可以共享项目状态，并在必要时通过 A2A 进行协商；
-   系统能够处理代码冲突、设计冲突、项目理解偏差和共享环境资源冲突；
-   Planning 是一种可变角色，而不是必须常驻、拥有最高权限的固定 Agent。

核心研究问题是：

> 如何在不牺牲 Coding Agent 自主性的前提下，让多个 Agent
> 逐步形成共同的项目认知，并可靠地协作修改代码和共享资源？

## 二、总体架构

系统由以下部分组成：

### 1. 用户与 Agent

Agent 通常由用户主动启动，而不是由 Planning Agent 自动拉起。

用户可以继续使用当前 Agent，也可以在当前工作区中启动新的 Agent，让不同
Agent 分别负责后端、前端、测试、审查或实验。

### 2. Agent Adapter

Adapter 负责让不同的 Coding Agent 接入同一个工作区，提供：

-   加入工作区；
-   获取与当前任务相关的项目上下文；
-   发送和接收 A2A 消息；
-   调用协调服务；
-   提交任务理解、设计方案、代码变更和验证结果。

Adapter 不应替代 Agent 自身的推理、编译器选择、测试选择和调试能力。

### 3. 协调运行时

协调运行时负责确定性和安全性问题：

-   项目状态和版本；
-   任务与依赖；
-   设计决策和契约；
-   代码变更记录；
-   文件范围与所有权；
-   资源租约；
-   冲突检测；
-   原子提交；
-   事件日志；
-   恢复和回滚。

Python 主要承担这些程序性职责，而不是代替 Agent 判断业务语义。

### 4. Project State

项目状态至少包括：

-   当前代码版本；
-   任务、依赖和任务状态；
-   已确认的设计决策；
-   API、数据模型和其他契约；
-   活跃 Agent 及其任务；
-   Agent 的理解、假设和不确定性；
-   已知冲突；
-   共享环境与资源状态；
-   决策和变更历史。

重要事实不能只存在于 A2A 聊天中，而应被固化到项目状态或决策记录中。

## 三、单 Agent 与多 Agent 应当共存

### 1. 单 Agent 主导模式

一个 Agent 可以自己完成：

-   理解需求；
-   制定计划；
-   划分任务；
-   修改代码；
-   运行编译和测试；
-   更新文档；
-   管理任务生命周期。

这种模式接近 Trellis 类工程工作流，应当是正式支持的默认模式。同一个
Agent 可以同时承担 Planning、Implementation 和 Validation。

### 2. 用户驱动的多 Agent 模式

当用户认为某项工作适合交给另一个 Agent 时，可以主动让新 Agent
加入工作区。

新 Agent 加入后：

1.  读取当前代码、文档和最近变更；
2.  获取与目标相关的项目上下文；
3.  自主理解需求；
4.  提出实现方案；
5.  声明影响范围、依赖、假设和不确定性；
6.  根据影响范围决定是否需要协调；
7.  开始实现并持续报告变化。

系统不应假设所有 Agent 都由 Planning Agent 创建或统一调度。

## 四、Planning Agent 的定位

Planning 是一种项目级协调职责，可以由独立 Agent、当前主 Agent 或其他临时
Agent 承担。

Planning Agent 主要负责：

-   维护项目级理解；
-   分析新方案的影响范围；
-   识别任务、设计、资源和 Agent 之间的关系；
-   发现不同 Agent 的理解差异；
-   提出任务边界和设计契约；
-   组织必要的协商；
-   记录正式决策；
-   在影响范围扩大时触发重新规划。

Planning Agent 不应直接代替实施 Agent
编写所有代码，也不应拥有绕过版本、权限、租约和审查机制的特权。

其他 Agent 应能够提出异议、纠正错误假设、要求重新规划和质疑任务划分。

## 五、新 Agent 的加入流程

新 Agent 不需要一加入就触发完整的全局规划。

建议采用"自主加入 + 增量协调"的流程：

1.  用户启动新 Agent；
2.  Agent 加入当前工作区；
3.  Agent 读取项目快照和相关上下文；
4.  Agent 自主探索和设计；
5.  Agent 提交简要的理解与方案报告；
6.  协调层分析影响范围；
7.  Planning 角色或相关 Agent 按需参与协商；
8.  系统根据风险确定任务边界、契约和权限；
9.  新 Agent 开始实施；
10. 执行过程中持续更新假设、变更和验证结果。

核心原则是：

> 新 Agent 先获得探索自由，再根据它实际触及的项目边界逐步获得执行权限。

## 六、按风险选择协调强度

### 1. 直接执行模式

适用于独立小功能、文档修改、影响范围很小的局部修改，以及不涉及公共契约或高风险资源的任务。

### 2. 辅助协调模式

适用于跨模块、可能影响其他 Agent、需要新增或修改
API、涉及数据结构或任务边界不清晰的任务。

### 3. 正式治理模式

适用于架构重构、数据库迁移、公共 API
重大变化、部署方式变化和破坏性环境操作。

因此，不是所有新功能都需要正式规划。

## 七、用户改变既有方案时的处理

用户提出新需求或改变既有设计时，不应让整个项目从头开始规划。

系统应：

1.  识别被改变的设计决策；
2.  创建新的设计或契约版本；
3.  找出依赖旧版本的任务和 Agent；
4.  分析代码、任务、资源和部署影响；
5.  通知受影响的 Agent；
6.  只暂停或重新规划受影响的部分；
7.  让不相关的任务继续执行。

变更的是某个设计决策的版本，而不是把整个项目状态清空。

## 八、冲突的范围

冲突不应只理解为 Git 文件冲突，还包括：

-   **文本冲突**：两个 Agent 修改同一段代码；
-   **设计冲突**：公共 API、数据模型或架构方案相互矛盾；
-   **认知冲突**：Agent 对项目现状、需求或模块职责理解不同；
-   **任务冲突**：任务边界重叠、依赖错误或前置条件被改变；
-   **资源冲突**：多个 Agent
    同时操作主机、数据库、端口、Docker、编译器、网络或部署服务。

其中，认知冲突是本项目最重要的研究对象之一。

## 九、共享代码区与 Worktree 的关系

Worktree 不是应当被消灭的旧方案，而是一种有价值的隔离级别。

共享代码区适合：

-   需要频繁协作的低风险修改；
-   已经明确的公共接口；
-   需要快速共享中间结果的任务。

Worktree 适合：

-   高风险重构；
-   实验性实现；
-   任务边界清晰的独立工作；
-   可能失败或需要大量试错的修改；
-   尚未完成理解协商的任务。

此外，还可以使用容器、临时虚拟机、独立数据库和独立部署环境。

目标不是证明共享代码区一定优于
Worktree，而是根据任务耦合度、风险、冲突率和协调成本，动态选择隔离方式。

## 十、A2A 的使用原则

Agent 之间可以通过 A2A
进行需求澄清、任务依赖询问、设计讨论、异议提出、变更通知、冲突协商、资源影响询问和验证结果共享。

推荐采用：

> 结构化消息外层 + 自然语言推理内容。

结构化部分用于表达消息类型、发送者、接收者、任务、项目版本、设计版本和影响范围。

自然语言部分用于表达 Agent
的理解、推理、假设、不确定性、方案比较和失败原因。

重要决策、最终契约和已确认事实必须写入 Project State 或 Decision
Log，而不能只停留在消息历史中。

## 十一、Agent 自主性与运行时强制的边界

### 由 Agent 负责

-   理解需求；
-   选择实现方案；
-   选择编译器和测试工具；
-   分析错误；
-   判断业务语义；
-   提出替代方案；
-   参与协商；
-   进行代码实现；
-   解释验证结果。

### 由运行时强制

-   版本一致性；
-   原子提交；
-   文件和任务权限；
-   资源租约；
-   危险操作审批；
-   状态机合法性；
-   事件记录；
-   回滚和恢复；
-   未授权操作拦截。

核心原则是：

> 运行时保护一致性和安全底线，Agent 负责需要理解项目语义的判断。

## 十二、已有方案的借鉴关系

### Trellis

作为单 Agent
工程生命周期和持久化工作流的参考，借鉴需求澄清、设计文档、任务生命周期、实现与验证记录以及工作区记忆。

### Worklode

作为确定性任务协调基础设施的参考，借鉴任务依赖、原子领取、租约、租约过期、任务状态、任务与交付物追踪以及可观测性。

但不直接采用所有任务都必须提前划分完成的强前置模式。

### amutix

作为用户主动加入工作区和轻量持久化协调的主要参考，借鉴 Agent
身份、工作区加入、共享上下文、任务评论、文件预留、交接和 journal。

### Agent Collab

作为 Worktree、任务交接、审查和合并流程的参考。

### AgentRoom、STORM、MPAC

作为共享状态、写入时协调、意图声明、冲突治理和结构化协作协议的研究参考。

本项目不应简单复制这些项目，而应将其成熟机制组合起来，并重点研究认知协作问题。

## 十三、项目的差异化方向

本项目的核心差异化是：

> 在用户主动加入多个 Coding Agent、单 Agent 工作流与多 Agent
> 协作并存的前提下，通过共享项目状态、增量 Planning、结构化意图、A2A
> 协商和可选隔离机制，处理由项目理解偏差引起的语义冲突。

主要研究方向包括：

1.  新 Agent 如何快速获得与任务相关的项目上下文；
2.  Agent 如何显式表达自己的理解、假设和不确定性；
3.  Planning 如何以可变角色参与，而不是成为固定总控；
4.  如何在不阻塞低风险工作的情况下发现高风险冲突；
5.  如何让 Agent 参与语义冲突解决；
6.  如何在共享代码区、Worktree 和隔离环境之间动态选择；
7.  如何处理用户对已实施方案的增量变更；
8.  如何通过事件和决策记录分析协调成本与收益。

## 十四、最终方案概括

-   用户驱动 Agent 加入，而不是 Planning Agent 统一拉起；
-   单 Agent 模式与多 Agent 模式共存；
-   Planning 是角色，不是固定实体；
-   新 Agent 先自主理解和设计，再按影响范围增量协调；
-   低风险任务直接执行，高风险任务正式治理；
-   中心化保存项目事实，A2A 用于 Agent 间协商；
-   运行时强制版本、权限、租约和安全边界；
-   Agent 负责理解、设计、实现、验证和语义判断；
-   共享代码区、Worktree、容器和 VM 都是可选隔离策略；
-   用户需求变化只触发受影响部分的重新规划；
-   通过可观测性记录操作、协作、认知和决策过程。

最终目标是形成一个既保留普通 Coding Agent 使用体验，又能够支持多 Agent
共同理解和协调的项目工作区。
