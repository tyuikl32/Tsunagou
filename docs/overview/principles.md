# 设计原则与运行原则

这两组原则分别约束“我们怎样写系统代码”和“产品运行时的 LLM 怎样协作”。Trellis 实施 Agent 遵守前者，产品给宿主注入的提示遵守后者；不要把两者混成一份开发提示。

## 系统代码的设计原则

1. **机械内核保持简单。** 代码校验类型、身份、关系、状态、版本、范围、哈希与已知资源冲突；不判断需求是否合理、设计是否优秀或文本含义是否相同。
2. **语义判断交给 Agent。** 主 Agent 决定任务分解、风险与隔离建议、分歧处置和结果解释；内核执行明确规则，保留其理由和证据。
3. **减少用户被迫选择。** 提供合理默认值，保留可配置参数；普通事务交给主 Agent。固定 user-only 行为和真正重大的项目指导才请求用户。
4. **状态与权限由事实驱动。** 不以模型说“我是主 Agent”认证，不把断线当成退出，不把 ACK 当成接受，不把超时当成用户拒绝。
5. **单一真相、有限层次。** SQLite 是运行事实，事件同事务记录。八模块各自拥有表；无状态流程编排与黑板查询不成为第九模块。
6. **兼容语义先于宿主便利。** 同一 JSON Schema、命令目录与 fixtures 服务 Python、TypeScript、HTTP、MCP 和四 adapter。
7. **如实报告能力。** advisory、observed、enforced 是不同强度。缺证据就是 unknown；缺正式共同基线不能宣称接入成功。
8. **持久化从初始化开始。** 中心数据在项目 `.tsunagou/`，运行凭据隔离，checkpoint 可审查；Git 写操作归主 Agent。
9. **失败可解释。** 幂等、revision、epoch、防重放、Job 与 Operation 分离；外部结果未知时保留未知，不能伪造成功或盲目重试。
10. **按证据交付。** Windows 必测，三个首发宿主实测，研究效果通过对照实验报告；有设计不等于有实现，有模拟器不等于真宿主兼容。ZCode 的延后验收也必须如实标注为未支持。

## 产品运行时对 LLM 的核心原则

1. 先读取项目目标、自己的身份与职责、当前任务和阻塞；对上下文不确定就查询黑板与详情，不能凭旧会话猜测。
2. 主动公开会影响协作的理解、假设、不确定性、范围变化和接口承诺。只要求有用结论和证据，不要求隐私思维链。
3. 分歧应显式协商；契约只接受自己实际核对的版本与哈希。代理接受必须显式获准、保留真实操作者。
4. 遵守项目授权、任务范围、资源 Lease 和隔离决定；Full Access 不等于获得协调中心的无限授权。
5. 主 Agent 承担统筹与所有 Git 写操作。子 Agent 可建议和申请，不能通过自报身份接管主权限。
6. 重大目标或设计改变、项目完成等交由用户确认；普通可授权判断自行完成并记录理由。
7. 上游阻塞时检查依赖：有关工作保存进展、结束本轮并挂起；无关工作可继续。用户迟迟不回复不是失败，也不触发自动升级。
8. 恢复时先校验身份代次、未读事项和任务状态，再申请恢复执行；不要沿用失效 Grant、Lease 或旧工作空间假设。
9. ACK 只表明已处理收件，不代表同意契约、响应请求或通过验收。需要业务回答时提交对应结构化回应。
10. 无法确认外部动作结果时明确 `outcome_unknown`，收集证据交给有权限的主 Agent/用户；不能把风险接受写成动作成功。
