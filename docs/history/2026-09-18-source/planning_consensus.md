# 规划阶段共识记录

> 本文档记录规划阶段的讨论结论、范围边界和待确认事项。每轮问答确认后及时追加；它是规划过程的工作记录，不替代项目设计文档。

## 规划目标

- 对多 Agent 协作工作区进行详细规划。
- 先对齐产品范围、模块边界、技术约束和验收目标。
- 暂不确定具体实现模式；后续再通过搜索和探索选择合适方案。

## 已确认共识

### 1. 首阶段用户与运行位置

- 面向个人用户。
- 多个 Coding Agent 在用户本机协作。

### 2. 首版首要验收目标

- 优先证明认知协作价值。
- 两个 Agent 能发现理解分歧、达成契约，并继续完成任务。
- 开发效率提升、代码与共享资源的可靠执行属于后续目标。

### 3. Agent 兼容与接入

- 首批兼容 2–3 种主流 Coding Agent，以验证适配层通用性。
- 允许安装适配器、修改 Agent 配置，并由本系统启动或附着 Agent。

### 4. 用户界面范围

- 当前项目先建设完整后端。
- Web 工作台属于后续接入方向，暂不纳入当前项目范围。
- 因此当前规划重点是后端能力、协议、状态和治理边界，而不是 Web 交互设计。

### 5. 技术与平台约束

- 后端语言确定使用 Python。
- 具体 Web/API 框架留待后续搜索和探索确定。
- 目标是跨平台本地服务。
- 首要支持 Windows，同时兼顾 macOS/Linux。

### 6. 项目范围与权限范围

- 不预设工作区必须对应单个 Git 仓库、固定文件夹或固定仓库数量。
- 一个项目跨多个文件夹、多个仓库属于常见情况，项目边界由用户决定。
- 调度中心和持久化数据需要有一个中心保存地点，但这不等于限制项目代码只能位于一个目录或仓库。
- 当“调度中心”和主 Agent 选择 Full Access 时，由负责管理调度中心的主 Agent 按用户意图决定可管理的项目文件夹范围。
- Agent 的可见范围和可写范围属于权限边界，由用户决定；不能由系统根据单仓库假设自动收窄或扩大。

### 7. 当前后端的业务边界

- 当前项目聚焦调度中心与协作内核。
- 内建项目状态、任务协调、认知协商、权限和持久化。
- 代码审查、部署等流程通过 Agent 或外部工具完成，不作为当前后端的完整内建工作台建设目标。

### 8. 权限、租约与运行时约束

- 第一阶段覆盖调度中心能够控制的文件夹、Agent 接入、任务状态和共享资源。
- Full Access 的具体范围由用户及主 Agent 决定。
- 运行时治理应围绕实际可控制边界执行，不假设系统能拦截 Agent 的所有本机操作。

### 9. 隔离级别

- 支持多种隔离级别，包括共享代码区、Worktree 及其他隔离环境。
- 初始选择为用户或主 Agent 按任务风险决定；第二轮已覆盖为“主 Agent 通过结构化 LLM 评估自动选择，内核复核硬约束”，用户可覆盖，主 Agent降级受项目策略约束。
- 首版正式驱动已确定为 shared、单仓库 Git Worktree 和只附着既有环境的 external；不实现跨仓库 Worktree 编排或容器生命周期管理。

### 10. 认知协调范围

- 第一阶段围绕 Agent 主动提交的理解、假设、不确定性和契约发现分歧。
- 系统需要支持组织协商和记录结果。
- 第一阶段暂不要求系统主动从代码、任务或对话中推断未声明的隐含分歧。

## 当前范围判断

- 当前项目是本地后端协调运行时及其 Agent 接入能力，不是完整 Web 产品。
- 核心验收围绕“两个 Agent 的理解差异协作闭环”展开。
- 适配层需要验证多 Agent 接入通用性，但不提前锁定具体框架或实现模式。
- 工作区模型应支持跨文件夹、跨仓库项目；中心化的是调度状态和持久化记录，而不是代码目录结构。
- 当前后端的产品边界是调度中心与协作内核，外部工具继续承担代码审查、部署等完整工程流程。

## 研究结果（2026-09-17）

详细研究已记录在 [agent_to_agent_deep_research.md](./agent_to_agent_deep_research.md)。本轮形成以下规划判断：

- 项目定位调整为“隔离策略无关的协调平面”：共享目录、Git Worktree 和后续其他隔离方式都是可选执行策略，协调层负责共享状态、认知契约、依赖、冲突和事件。
- 不把“共享代码区优于 Worktree”作为前提。2026 年 CAID 研究显示，Worktree 隔离在两个基准上均优于共享工作区的软约束，但协调和串行集成会增加成本；本项目的效率优势必须通过对照实验验证。
- 内部领域模型是项目状态的权威来源。MCP 用于 Agent 与协调服务的工具/资源接入，A2A 留作后续跨 Agent 系统或跨机器边界；两种协议都不直接替代内部任务、权限、租约和契约模型。
- 截至 2026-07-28 的 MCP 已将 Roots 标记弃用，Tasks 也属于可选扩展。因此多文件夹/多仓库范围由本系统的项目清单、显式参数和资源标识表达，不依赖 MCP Roots 或 MCP Tasks。
- 首阶段采用 Python 模块化单体；建议划分为项目空间与权限、Agent 接入、任务调度、认知协商、资源协调、隔离驱动、持久化回放、可观测性与评估八个一级模块。
- 将运行时治理按能力分级：通知型、观察型、工具门禁型、隔离型。Full Access 或适配器覆盖不足时，只能声明协调/检测能力，不能声称已完整强制。
- 产品 MVP 仍以两个 Agent 的认知分歧闭环为首要目标；原题的正式对照验收必须使用至少三个 Agent，并与单 Agent、独立 Worktree 多 Agent比较。
- 正式实验增加一组“关闭认知报告与契约协商”的消融条件，用于区分一般任务调度收益与本项目核心认知协作收益。
- Python/TypeScript 依赖与本机工具链的 2026-09-17 注册表快照另见 [technology_stack_research.md](./technology_stack_research.md)；该快照用于选择兼容窗口，不等同于最终锁文件。

## 实现细化阶段的已确认变更（2026-09-17）

本轮逐项回答记录在 [implementation_decisions.md](./implementation_decisions.md)，后续继续追加。以下更新覆盖前文的早期未定状态，早期内容保留作为历史。

- 已选择单一用户级守护进程、HTTP + SSE 核心接口和 MCP 适配边界。
- 技术栈已确定 Python 3.13 + uv、FastAPI + Uvicorn、SQLite + SQLAlchemy 2 + Alembic。
- 采用事务状态与同事务领域事件，强制乐观并发，REST 资源与显式状态转换。
- 采用每 Agent 持久收件箱、逐消息确认、直达/订阅/影响路由，以及按能力推送并回退拉取。
- 数据使用平台标准用户目录且允许覆盖；CLI 管理守护进程并支持按需自启。
- 首版信任同一 OS 用户，治理正常 Agent 的授权操作，不承诺抵御同账户恶意进程。
- 用户最新名单按四款产品理解为 Codex、OpenCode、ZCode、DeepSeek Harness；暂不考虑 Claude Code。用户已确认四种均达到正式共同基线，主动唤醒与工具门禁按宿主能力增强。
- 身份绑定项目周期和具体对话上下文；同厂商新建空对话重新接入；主 Agent 确认继承关系后方可重新分配旧任务；同厂商多对话可并存为不同身份。
- 原会话恢复或上下文压缩仅在宿主提供可验证连续性证据时保留身份；新建、清空和分叉会话创建新身份，分叉只保留来源关系；无法验证时重新接入。
- 早期继任结论已由 D124-D128 细化并部分覆盖：整体/按任务继任会新建 Attempt，不转移 Lease、workspace 或 grant；全部 pending obligations 自动替换给 successor；契约参与者变化创建新 proposal hash 并要求全体重签；历史作者与旧接受记录不改写。
- Project 是持续到用户归档或删除的长期协作空间；项目成员身份与一次性加入票据、本机 HostSession 凭据分离。首发 session token 随会话失效，不实现 access/refresh token 轮换。
- 每个项目同一时刻最多一个主 Agent；用户始终可任免，项目策略允许时主 Agent可原子交接；每次交接递增授权代次，旧管理命令失效，离线不自动选主。
- 用户分别设置调度中心和主 Agent 的权限上限，普通 Agent 权限取交集；只有用户能扩大上限。宿主可为避免 IDE/Harness 限制而保持 Full Access，但调度中心必须如实区分自然语言约束、观察、工具门禁和真正隔离，不能虚报机械保护。
- 执行强度按资源能力分为 advisory、observed、gated、isolated；任务可要求最低级别，不满足时不能自动分派。项目可允许主 Agent 留理由降级，也可开启严格模式禁止降级。
- 权限协议采用固定 capability 与带范围授权，角色仅为模板；系统、用户、项目、主 Agent 和任务授权逐层取交集，显式拒绝优先；首版不引入通用策略脚本。
- 项目用多个具名 ProjectRoot 表示跨目录/跨仓库范围，内部使用 root 相对资源 URI；路径按平台规范化并处理链接逃逸，同一物理目标去重，Full Access 单独显式表达。
- 每个项目从初始化起就在用户指定的协调根中建立项目内持久化，基本协作上下文随项目维护；用户级目录只承担守护进程发现和项目索引，不能成为项目状态的唯一保存地点。
- 项目内 `.tsunagou/` 分为 Git 共享层与默认忽略的 `local/`：共享层保存清单、逻辑 roots、策略、任务/契约/认知快照、已完成事件段和检查点；本机层保存 SQLite、令牌、连接、活跃租约和缓存。新克隆从共享层恢复并开启新运行代次。
- 协作事务通过 outbox 原子物化共享文件；已提交但未物化的命令返回 pending 状态。交接、完成、归档和 Git 提交前必须通过 checkpoint。调度中心不自动 commit、merge、pull 或 push。
- checkpoint 以父哈希形成历史链，外部 Git 状态只有 fast-forward 才自动导入；分叉时停止写入并做实体级三方合并，同实体冲突由主 Agent 处理，身份与权限上限冲突由用户处理，活跃运行态不参与合并。
- Git 共享层用 TOML 保存人工配置、用带 JSON Schema 版本的 JSON 保存权威快照、用 NDJSON 保存封存事件；JCS + SHA-256 校验内容，Markdown 只作为派生阅读视图，首版不使用 YAML 或数字签名。
- 持久 ID 使用 UUIDv7；聚合 revision 负责并发，本机 runtime_epoch/event_seq 负责 SQLite 与 SSE 顺序，checkpoint 父哈希和因果字段负责跨克隆历史；UTC 时间戳不作为顺序权威。
- REST、MCP 与插件共享应用命令信封；命令以 UUIDv7 command_id 幂等、expected_revision 并发，错误采用 RFC 9457，主版本进入 URL，异步完成以 202 operation 表达。
- 收件箱分别记录入队、投递租约、宿主获取、可证明的模型可见、业务确认、延后、过期和死信；确认不代替请求所要求的结构化响应。
- 消息只定义 notification/request/response 三种顶层语义；request 有结构化响应契约，路由在发送时固化为逐 Agent 收件记录，历史回放显式进行，优先级不改变权限。
- 第二轮第 28 至 136 题已完整记录在 [implementation_decisions_round2.md](./implementation_decisions_round2.md)：任务采用开放领取的扁平安全状态机和不可变 attempt；认知协商采用关键边界报告、确定性分歧检测、逐一接受的不可变契约；资源采用意图/租约分离和原子全取。
- 隔离驱动正式支持 shared、单仓库 Worktree 和只附着的 external；主 Agent通过结构化 LLM 请求评估风险，内核复核硬约束。SQLite 每项目单库、OS 单写锁、WAL+FULL、持久作业和同事务 outbox。
- 四种适配器采用宿主原生薄桥接与统一 REST/SSE/Schema；附着是共同基线，托管启动是增强。源码 monorepo 运行、显式登记 runtime。首发只监听 loopback，control token 与逐 HostSession token 只标识主体，所有角色、任务 owner 和 scope 由服务端状态授权；不做 OAuth/JWT/TLS/refresh 或浏览器认证。
- 首发安全目标是防止正式 API/MCP 上的误用和身份混淆，不抵御同一 OS 用户下拥有 Full Access 的恶意进程。子 Agent不能通过自报 role/agent/task 字段成为主 Agent或接管主 Agent正在运行的 TaskAttempt。
- 依赖采用兼容范围与精确 lockfile；JSON Schema 2020-12 是跨语言协议源，生成 Pydantic v2 和 TypeScript 类型；Python 3.13 的 UUIDv7 使用封装后的 `uuid6`。
- 默认日志仅采集元数据并支持 OTel；实验使用微基准和 A/B/C/D 真实仓库对照。真实 Agent 首版手工验收，Windows 是唯一阻塞发布的平台。
- 当前目标是继续决策并编写八模块详细实现计划，之后用户再启用 Trellis；尚未开始产品代码实现。
- 第 211–227 题已写入 [implementation_decisions_round2.md](./implementation_decisions_round2.md) 的 D135–D151，并汇总于 [agent_autonomy_blackboard_resume_protocol.md](./agent_autonomy_blackboard_resume_protocol.md)：逻辑继任与外部收敛分层，主 Agent在用户总体边界内默认自治，重大事项通过持久 UserDecision 阻塞；子 Agent可提交阶段结果并挂起，依赖满足后自主请求恢复；blocked 状态仍可提交协调材料，契约代行保留真实代理主体。
- 第 228–236 题已写入 D152–D160，并汇总于 [project_completion_protocol.md](./project_completion_protocol.md)：普通Task由协作角色验收，项目整体完成由Agent提议、用户确认；completed可由user或策略授权的current main重激活；历史任务只按显式批量选择直接恢复为open。业务适用性和完成前未完成工作的处置由主Agent判断，内核只守身份、revision、终态、唯一owner/Attempt和“无合法执行权仍存活”等结构不变量。
- 已建立规范性总纲 [design_and_runtime_principles.md](./design_and_runtime_principles.md)，明确区分约束项目代码的设计原则与约束投入运行后LLM行为的核心原则。后续八模块计划、协议Schema、运行时提示词和验收用例均须逐项映射该总纲。
