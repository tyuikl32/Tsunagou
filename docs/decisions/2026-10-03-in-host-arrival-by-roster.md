# D194 "宿主自己接入"那类申请的到达判定：按名单，并把基线记下来

日期：2026-10-03
状态：已实施

## 决定

控制台里"这次接入到底到没到"原先只有一条判定：**Codex 的认领 + 回执**。DeepSeek Harness
（以及任何 `in_host` 的宿主、以及跨机器邀请）根本不走那条链 —— 主机这边**什么都不写**，
于是页面的等待框等到票过期也不会翻绿（测试同事报的正是这个）。

现在分两条判定，**由记录本身决定用哪条**：

| 记录的来源 | 到了没有，由什么判定 |
|---|---|
| Codex 的申请（`console` 模式，会被某个聊天认领） | 不变：认领 + 桥写回执，主机核对回执（`_receipt_matches`） |
| 宿主自己接入（`in_host`）、跨机器邀请（`network`） | **名单比对**：申请时不在、现在出现、身份对得上、角色对得上的那个席位 |

两条判定的判据是"这条记录里有没有**基线**"（申请时名单上有谁）。为此：

- 机器级记录在创建时多写一个 `baseline`（当时名单上的 `agent_id` 列表）✓；
- 申请那一刻读不到名单（daemon 还没起）就先不写，等第一次读得到时**补记**下来
  （`note_baseline`）——宁可多等一轮，也不把本来就在那儿的席位当成刚到的人 ✓；
- 身份归属沿用 `observe` 那条出口已有的规则：**档案里从接入文件学到的厂商**要对得上；
  唯一例外是"自己报了机器名"的席位（跨机器邀请在这台机器上什么都不写，机器名就是它
  唯一的归属证据，而那是 daemon 入席时观察到的）✓；
- 页面与控制台**共用同一个判据**（`_attributed_seat`），不许各说各话 ✓。

同一批还修了页面两处把宿主说错的地方：

- `in_host` 的申请以前不认，被说成"这个宿主要人手工补一条命令"（对 DSH 是错的：它只要在
  自己聊天里说一句话）✓；
- 刷新恢复时把申请**写死成 Codex** 继续等 —— 于是等的是一个它永远不会有的回执，而且到达
  时会把厂商记成 `Codex`（页面从此给这个 Agent 画另一家的图标）✓。

## 为什么不直接给 DSH 补上认领 + 回执（原方案 B）

那才是"这次接入就是页面上那次"的**凭据**，比名单比对强。但它要定几件事：DSH 的会话号只有
宿主自己知道，认领由插件发起还是 CLI 发起、回执由谁在什么时刻写、写在哪里。那是协议层面的
决定，不该顺手做。这一轮先把"等待框永远不翻绿"解决掉，并**如实标明**这条判定看到的是什么
（名单），不假装它是回执。

另一半也已经落地（`646305a`，另一支提交）：`tsunagou_connect` 先读机器级记录，用记录里的
`project_root` 去连，而不是拿聊天的工作目录去猜项目。

## 落点

- `platform/enrollment_store.py`：`create(baseline=…)`、`note_baseline(…)`；
- `console/enrollment.py`：`_attributed_seat`（两条出口共用）、`_watch_roster`（名单判定）、
  `_roster_ids`（申请时取基线）、`_intent_status` 按"有没有基线"分流、`_waiting_note` 按宿主
  说话；
- `web/assets/js/behavior.js`：`in_host` 也算"等着就行"；刷新恢复按记录自己的宿主继续等；
  等待措辞按宿主判（不再写死 Codex）；
- 测试：`tests/unit/test_console_enrollment.py`（名单到达 / 老席位不算到达 / 角色不对 /
  远端靠自报机器名 / 基线补记 / 两条出口判定一致）、`web/tests/behavior.smoke.test.ts`
  （刷新恢复一条 DSH 申请：不重新准备、等那条会翻绿的出口、到达时厂商记它自己那家）。
